Identify an immutable candidate

The accepted packaging implementation inspects actual Docker-save bytes and source identity. Its private candidate inventory uses these exact names:

  • runtime-manifest.json — source commit/tree, source archive, input lock, interface versions and real image hashes/sizes.
  • health-buddy-linux-amd64.docker.tar and health-buddy-linux-arm64.docker.tar — distinct native Linux image-save archives.
  • health-buddy-source.tar — selected immutable source and matching docs.
  • SHA256SUMS — actual manifest and artifact hashes.

No archive or private verification receipt is linked here. Obtain the exact admitted candidate and trust evidence through your owner-controlled delivery process. A hash binds bytes; it does not independently identify their publisher. Never replace the manifest with a version label or resolve a moving image tag.

Check the actual host

The runtime targets an already-running native 64-bit Linux AMD64 or ARM64 host. Physical Raspberry Pi qualification, OS support matrix and final installation resource requirements remain release gates. Native Windows server support is not established. Do not use Windows-mounted workspaces, unqualified emulation or silently remapped ownership.

The owner must independently admit the local Docker CLI, Compose plugin and Unix-socket daemon. The complete workspace is a private native 0700 directory owned by the selected nonzero service UID/GID. Existing directories are not recursively adopted, chmodded or chowned. The image and personal workspace are separate.

What an owner would review

After independently obtaining the selected verified source and actual candidate artifacts, the implemented loader can create an absent private environment file with the observed immutable engine image ID. The following is an owner-review reference, not a command to install from this website:

python scripts/package_runtime.py load --manifest "$ARTIFACTS/runtime-manifest.json" --architecture amd64 --workspace "$OWNER_WORKSPACE" --uid "$SERVICE_UID" --gid "$SERVICE_GID" --docker /usr/bin/docker --output-env "$PRIVATE/runtime.env"

ARTIFACTS must be the admitted private artifact directory; OWNER_WORKSPACE an existing private native workspace; SERVICE_UID/GID its nonzero owner; PRIVATE a private native output directory. Run from the exact verified source, not a mutable branch. ARM64 selects --architecture arm64 and its matching archive. Inspect the exact supported helper.

The maintained Compose recipe uses that verified ID with no tag pull, a read-only image, bounded resources and an external workspace bind. API and finite jobs share the canonical coordinator; loading or enabling an extension does not create a schedule.

Sign in and approve each boundary

  1. Approve host changes and a pinned candidate before setup; preparing a bare Pi/OS is outside this scope.
  2. Join the private network yourself and review HTTPS origin/access policy; these scripts do not configure Tailscale, TLS or Serve.
  3. Set up separate application owner authority; network membership alone is not health access.
  4. Grant only the agent scopes and selected context you approve. Maintenance authority remains a separate native owner permission.
  5. Enable optional sources individually. Phone pairing and Health permissions remain explicit; no companion download is promised.

Keep the workspace useful locally

The runtime contains its selected source, contracts and documentation. Daily dashboard/logging does not require this site, an agent session or optional AI enablement. Bring your agent for bounded questions, deliberate record edits, troubleshooting or a maintained addition. Follow the pinned customization walkthrough.

Keep a coordinated encrypted backup of the whole external workspace. Source/tests/notes/state are part of recovery, not disposable image files. Read the exact backup and clean-host restore policy; restored credentials require explicit re-pair/re-key, and arbitrary private core edits still need review.
