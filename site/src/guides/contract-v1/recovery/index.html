Keep a recoverable workspace.

A successful restore should bring back useful behavior, not just a similar row count.

Planned troubleshooting checks

Versioned diagnostic commands and exact repair steps are pending the delivered runtime. This guide provides no executable repair command.

Back up the complete authoritative inventory

A consistent encrypted snapshot must include dataset identity, canonical stores, operation journal and retry ledger, personal source, assets, configuration, tests, notes, migrations, state and required secrets. Preserve file modes and secret permissions. Disposable caches may be excluded only when their reconstruction is tested.

Backup verification compares inventory, digests and behavior. A successful file copy or a merged PR does not prove clean-host recovery.

Restore data without reviving old authority

Every restore creates a fresh security epoch after the backup is read, including an in-place restore. Rotate restored grants and re-pair phones. Old prepared writes, caches and phone anchors must not silently apply to the restored epoch. A revoked credential must not become valid because an older backup contained it.

Replacement-phone history needs reviewed source reconciliation. Uncertain history is not silently doubled or treated as an empty new series.

Preflight an update before activation

Match the actual release, data schema and extension API. Use isolated migration copies and retain rollback inventory. Incompatible extensions block activation unless you explicitly disable them with files and state intact. A core fork requires deliberate rebase and retesting.

Qualification still needs a clean host, both supported agents, useful extension behavior and a post-backup revocation test. Physical phone acceptance and deployment remain separate gates.
